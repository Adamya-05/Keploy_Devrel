## What is Keploy?

Most API tests are written by hand — you write a request, hard-code an expected response, mock out the database, and repeat for every endpoint. It works, but it drifts from reality the moment someone changes a query or adds a field.

Keploy takes a different approach. It sits between your application and its dependencies (MongoDB, PostgreSQL, Redis, external APIs) and records every real interaction while your app runs. Those recordings become your test cases and mocks. When you replay them, Keploy stubs the database with the recorded responses, so your tests pass without a live database and without any mocking code you had to write yourself.

The result is a test suite that reflects what your app actually does, generated in the time it takes to make a few curl requests.

## Prerequisites

Before you start, make sure you have these installed:

| Tool | Why you need it |
|------|----------------|
| [Go 1.21+](https://go.dev/dl/) | Running the sample application |
| [Docker Desktop](https://www.docker.com/products/docker-desktop/) | Running MongoDB in a container |
| [Keploy CLI](https://keploy.io/docs/server/installation/) | Recording and replaying tests |
| Git | Cloning the sample repo |

<Callout type="warning" title="Platform note">
The native Keploy CLI runs on Linux and macOS. On Windows, use WSL2 or run everything inside Docker. If you're on WSL2, start it first:

```bash
wsl ~
```
</Callout>

## Installing Keploy

```bash
curl --silent --location "https://github.com/keploy/keploy/releases/latest/download/keploy_linux_amd64.tar.gz" | tar xz -C /tmp
sudo mkdir -p /usr/local/bin && sudo mv /tmp/keploy /usr/local/bin
keploy --version
```

On Apple Silicon (M1/M2/M3), replace `linux_amd64` with `linux_arm64`.

<Callout type="tip" title="Always check --help against your installed version">
The CLI docs can lag behind releases. If a command fails, run `keploy --help` first — it shows exactly what flags your installed version supports.
</Callout>

## Recording test cases

This is where Keploy does its thing. Instead of writing `_test.go` files, you run your app under Keploy and make real API calls.

<Callout type="info" title="What keploy record actually does">
Keploy uses eBPF to hook into your process's syscalls. It intercepts both the inbound HTTP requests from curl and the outbound MongoDB wire protocol calls. Every request/response pair gets written to a YAML file under `./keploy/`.
</Callout>

<Steps>

<Step number={5} title="Start the app under keploy record">

```bash
keploy record -c "go run main.go handler.go"
```

The `-c` flag is the command Keploy uses to run your app. Keploy wraps your process so it can intercept all network traffic.

<Step number={6} title="Make API calls to generate test cases">

Open a second terminal and hit the endpoints. Each call becomes a recorded test case.

**Shorten a URL:**

```bash
curl --request POST \
  --url http://localhost:8080/url \
  --header 'content-type: application/json' \
  --data '{"url": "https://github.com/keploy/keploy"}'
```

Response:

```json
{
  "ts": 1696173347,
  "url": "http://localhost:8080/Abc1XyZ2"
}
```

**Follow the shortened URL** (copy your short code from the response above):

```bash
curl --request GET http://localhost:8080/Abc1XyZ2
```

Make a few more POST requests with different URLs to build a richer test suite, then stop recording with `Ctrl+C`.

</Step>

<Step number={7} title="Inspect what Keploy recorded">

After stopping, look at the `./keploy/` directory:

```bash
ls ./keploy/test-set-0/tests/
# test-1.yaml  test-2.yaml  test-3.yaml
```

Open `test-1.yaml`:

```yaml
version: api.keploy.io/v1beta2
kind: Http
name: test-1
spec:
  req:
    method: POST
    url: http://localhost:8080/url
    header:
      Content-Type: application/json
    body: '{"url":"https://github.com/keploy/keploy"}'
  resp:
    status_code: 200
    body: '{"ts":1696173347,"url":"http://localhost:8080/Abc1XyZ2"}'
  assertions:
    noise:
      - body.ts
      - header.Date
```

And `mocks.yaml` contains the exact MongoDB wire protocol messages that were exchanged — Keploy will replay these instead of hitting a real database.

<Callout type="tip" title="The noise field matters">
`body.ts` is a timestamp that changes on every run. Without marking it as `noise`, the test would fail every time. Keploy auto-detects some noisy fields, but if you see a failure from a changing field, add it to the noise list manually.
</Callout>

</Step>

</Steps>

## Running tests

<Steps>

<Step number={8} title="Run keploy test">

```bash
keploy test -c "go run main.go handler.go" --delay 10
```

`--delay` gives your app time to start before Keploy fires requests. Ten seconds is enough for a Go app.

<Terminal title="Terminal output">
{`🐰 Keploy: Running tests...

Test Set: test-set-0
  Running test-1... PASSED ✅
  Running test-2... PASSED ✅
  Running test-3... PASSED ✅

Summary: 3 passed, 0 failed
Test run: PASS`}
</Terminal>

Keploy replayed the recorded HTTP requests, substituted all MongoDB calls with the recorded mocks, and verified the responses matched.

</Step>

<Step number={9} title="Handle test failures (if any)">

If a test fails, the output tells you exactly what didn't match:

```
FAIL: test-1
  Expected: {"ts":1696173347,"url":"http://localhost:8080/Abc1XyZ2"}
  Actual:   {"ts":1696184512,"url":"http://localhost:8080/Abc1XyZ2"}
  Diff: body.ts
```

Fix it by adding `body.ts` to the noise list in the test YAML, then re-run.

<Callout type="warning" title="Common failure causes">
- Timestamp or ID fields changing — mark as `noise`
- App hasn't started yet — increase `--delay`
- MongoDB container stopped — run `docker ps` and restart if needed
- Port 8080 already in use — check with `lsof -i :8080`
</Callout>

</Step>

</Steps>

## What happened under the hood

When you ran `keploy record`, Keploy used eBPF to hook into your process's network syscalls. Every time your app called MongoDB — a `find`, an `upsert`, a `delete` — Keploy captured both the request and MongoDB's response. It also captured the incoming HTTP requests from curl.

When you ran `keploy test`, Keploy:

1. Started your app
2. Replayed the recorded HTTP requests
3. Intercepted every MongoDB call and returned the recorded response instead
4. Compared the HTTP response your app produced against the recorded one

The MongoDB container was not involved during the test run at all.

This matters because:

- **Tests are fast** — no network round-trips to a real database
- **Tests are stable** — fixed data, no flaky failures from unexpected DB state
- **No mocking code** — mocks come from real behavior, not assumptions
- **Coverage by default** — every code path that handled a real request gets covered

## Going further

**Add edge cases.** During recording, try invalid inputs: a missing URL field, a short code that doesn't exist, a malformed request. Each curl call becomes another test case automatically.

**Integrate with CI.** Add `keploy test` to your GitHub Actions workflow. Because tests don't need a live database, they run cleanly in any environment.

**Read the generated YAML.** The test files are plain text — edit them to add assertions, change expected status codes, or test error handling. Keploy generates them, but you own them.

**Try other quickstarts.** The [samples-go repo](https://github.com/keploy/samples-go) has Echo + PostgreSQL, Chi + PostgreSQL, gRPC, and more. The workflow is identical regardless of stack.
